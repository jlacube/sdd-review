# R-002 — Spec-driven tools and new paradigms for reviewing code changes at scale

## Question
Brief (step 3, Research and discovery): produce a sourced note on two topics that feed a "disruptive" review workflow.

1. Spec-driven development (SDD) tools and how they verify that code matches a spec: GitHub Spec Kit, AWS Kiro, Tessl, BMAD-METHOD, Agent OS, OpenSpec and similar; spec-to-code traceability approaches (requirements tracing, acceptance tests as evidence, Gherkin/BDD); what each offers at review time.
2. Evidence and ideas on reviewing large changes differently: empirical research on review effectiveness versus change size (Cisco/SmartBear, Google and Microsoft modern code review), cognitive load, review ordering and partitioning (untangling composite changes), risk-based review and review-by-exception, intent-level or narrative walkthroughs, test- or runtime-evidence-based acceptance, provenance (agent transcripts as review input), and 2024–2026 writing on reviewing AI-generated code at scale. End with 10–20 candidate paradigms.

Why asked: P-01's round-1 answers (questions log) set the primary reviewer to the developer reviewing agent output locally, specs used when present with an intent fallback, a wide survey, and a wish for a disruptive workflow and UI because the number and size of changes grow fast. This note feeds the options analyses and the problem statement of CHG-001. AI PR-review bots and diff/stacked-review UIs are out of scope here (parallel note). No form factor is recommended.

## Findings

### A. SDD tools and spec-to-code verification

- Spec Kit separates a pre-implementation consistency check from a post-implementation conformance check. The knowledge base reports `/speckit.analyze` (read-only report of conflicts, gaps and ambiguities across `spec.md`, `plan.md`, `tasks.md`), `/speckit.checklist` (a checklist reviewing requirement quality, not code) and `/speckit.converge` (assesses code against spec, plan and tasks, presents severity-graded findings, appends traceable tasks to `tasks.md` when gaps remain, loops with implement until "Converged"). The repository README lists the converge command and the "Converged" outcome but does not list analyze or checklist as commands. — sources: https://deepwiki.com/search/99904c9e-39f0-4db6-9eed-a960f29c004d (2026-11-17), https://github.com/github/spec-kit (2026-11-17) — confidence: medium (README confirms converge; analyze and checklist rest on the knowledge-base summary alone)
- Spec Kit's review-time output is a findings report plus extra tasks in a markdown file; no code-to-requirement view for a human reviewer is described. — sources: https://deepwiki.com/search/99904c9e-39f0-4db6-9eed-a960f29c004d (2026-11-17) — confidence: low (absence in one AI summary; inference)
- Kiro keeps three files per feature spec (`requirements.md`, `design.md`, `tasks.md`; `bugfix.md` for bug fixes). Tasks run individually or in dependency-ordered parallel waves. Reviewers comment on passages of the requirements and design documents and send the comments to the agent together ("Markdown Review"). An "Analyze Requirements" step checks requirements for inconsistencies and gaps before design. — sources: https://kiro.dev/docs/specs/ (2026-11-17) — confidence: high (official documentation)
- Kiro's property-based testing (IDE only, optional by default) turns each EARS requirement into properties, runs them against hundreds or thousands of random inputs, and shows a shrunk counter-example on failure. In the design view a property links to its requirement and task, and a test links to the code it exercises. The page states this is evidence, not proof, and a weak property can pass while behaviour is wrong. — sources: https://kiro.dev/docs/specs/correctness/ (2026-11-17) — confidence: high (official documentation)
- Kiro's requirements use EARS notation (WHEN … THEN … SHALL …) and tasks are linked to requirements, per secondary sources; the official specs page did not mention EARS or the task-to-requirement link. — sources: https://sdtimes.com/ai/amazon-launches-spec-driven-ai-ide-kiro/ (2026-11-17), https://www.verdent.ai/guides/agents/kiro-spec-driven-development (2026-11-17) — confidence: low (secondary and blog sources from a search snippet; not opened in full)
- Tessl is two products: a Spec Registry (versioned specs describing libraries, open beta at launch) and a Framework (spec-first workflow via MCP, closed beta at launch). A Tessl spec carries a list of capabilities with linked tests; `@generate` marks a spec that generates code, `@describe` one that documents existing code. The launch post gives no detailed mechanism for verifying code against the spec beyond "tests to enforce guardrails". — sources: https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry/ (2026-11-17) — confidence: medium (vendor primary page, product status may have changed since launch)
- An independent assessment of the three tools classifies Kiro, Spec Kit and Tessl as spec-first, only Tessl aspiring to spec-anchored and spec-as-source (humans edit only the spec; generated code marked "GENERATED FROM SPEC - DO NOT EDIT"). The author reports that Spec Kit output was "very verbose and tedious to review", that the agent did not reliably follow the spec (it ignored notes and created duplicates), and "I'd rather review code than all these markdown files". She concludes that a spec-driven tool would need "a very good spec review experience". — sources: https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html (2026-11-17) — confidence: high (opened primary article, but a single author's hands-on experience on small tasks; the date of the article was not shown on the fetched page)
- BMAD-METHOD offers several review layers. `bmad-build` runs a review (none, quick, or thorough: four independent lenses — bare-diff adversarial, edge cases, verification gaps, intent alignment). `bmad-code-review` reviews a PR, branch, commit or diff and records findings in the plan. `bmad-walkthrough` guides a human through a change block by block without severity or verdict. A `verification-gap` lens checks whether changed behaviour is protected by tests. Formal requirements-to-test traceability is left to an optional TEA module. — sources: https://deepwiki.com/search/45474b47-9edf-4af8-b7aa-807a0e185c28 (2026-11-17) — confidence: medium (single AI-generated repository summary; matches the brief's expectation of lens-based review)
- OpenSpec stores a change as a folder (proposal, design, tasks, delta specs) and expresses spec changes as deltas (ADDED, MODIFIED, REMOVED, RENAMED) so a reviewer sees changed behaviour, not the whole spec. `/opsx:verify` is advisory and reports Completeness, Correctness and Coherence with CRITICAL, WARNING or SUGGESTION levels. It labels missing evidence "Not verified" and unsupported checks "Not applicable", and says neither is a pass. Archive merges the deltas into the main specs. Verify is available only in the expanded profile. — sources: https://deepwiki.com/search/0ec33dff-51cd-47b5-af4b-8786e760dd53 (2026-11-17) — confidence: medium (single AI-generated repository summary)
- Agent OS v3 uses Plan Mode plus `/shape-spec`, `/discover-standards` and `/inject-standards`; the available documentation describes no automatic check of the implementation against the spec, and its changelog records that v2.1 removed routine spec verification. — sources: https://deepwiki.com/search/081f141a-6bea-47d6-a37d-caf224a4d679 (2026-11-17) — confidence: low (the summary itself says the v3 instructions were not in its context)
- In the sources opened, the tools' conformance checks are run by an agent or by tests inside the author's workflow (converge, verify, lenses, property tests). None was found that presents a human reviewer with a requirement-by-requirement coverage view over a large diff. — sources: https://deepwiki.com/search/99904c9e-39f0-4db6-9eed-a960f29c004d (2026-11-17), https://deepwiki.com/search/0ec33dff-51cd-47b5-af4b-8786e760dd53 (2026-11-17), https://kiro.dev/docs/specs/correctness/ (2026-11-17) — confidence: low (inference from absence; products change fast and the tools were not run)
- Practitioner guides split spec drift into structural drift (a requirement with no test, a behaviour change with no spec update; detectable mechanically) and semantic drift (a test exists but code and spec disagree; needs an agent audit). They propose requirement IDs that at least one test references, with CI failing on untested or orphaned IDs, and a verifier separated from the implementing agent. — sources: https://developertoolkit.ai/en/workflows/plan/spec-driven-development/ (2026-11-17), https://www.augmentcode.com/guides/spec-tdd-shippable-ai-generated-code (2026-11-17) — confidence: low (vendor and practitioner blogs from search snippets, not opened in full)
- Gherkin scenarios are used as executable specifications: the scenarios run in CI, so a mismatch shows as a failing test, and reporting tools (Serenity BDD, Pickles, LivingDoc) and test-management platforms add requirement-to-scenario traceability. One source warns that an HTML report alone is a test report, not living documentation. — sources: https://www.accelq.com/?p=34357 (2026-11-17), https://qaskills.sh/blog/living-documentation-bdd-cucumber (2026-11-17) — confidence: low (vendor-adjacent blogs from search snippets)
- Traceability, as defined by the community of practice cited in the 2014 "Software traceability: trends and future directions" paper, is the ability to relate any uniquely identifiable software artifact to another, keep the links over time, and use the network to answer product and process questions; many certifying bodies require it in safety-critical systems. — sources: https://scholars.uky.edu/en/publications/software-traceability-trends-and-future-directions/ (2026-11-17) — confidence: medium (bibliographic record and snippet; full paper not opened)
- Formal route: the vericoding benchmark (arXiv 2025, 12,504 formal specifications in Dafny, Verus and Lean) asks a model for code plus a machine-checkable proof from a formal spec; reported success was highest in Dafny (about 82% in one summary, 67–82% in another), much lower in Verus and Lean. — sources: https://arxiv.org/abs/2509.22908v1 (2026-11-17), https://alphaxiv.org/benchmarks/mit/vericoding-benchmark (2026-11-17) — confidence: low (search snippets only; figures differ between summaries; benchmark problems are small algorithmic tasks)

### B. Evidence on reviewing large changes

- The Cisco/SmartBear study (2006) recommends reviewing no more than 200 to 400 lines at a time and an inspection rate below about 300–500 lines per hour; a 200–400 line review over 60–90 minutes is expected to find 70–90% of defects. SmartBear's page presents the 70–90% as an expectation, not a measured result, and does not give the study size; search summaries give about 2,500 reviews and 3.2 million lines. Reviewing 20–33% of the code (spot checking) is said to lower defect density with little time. Authors annotating their own code before review is said to help reviewers and to lead authors to find errors themselves. — sources: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/ (2026-11-17), https://agileconnection.com/article/largest-case-study-code-reviews-ever (2026-11-17) — confidence: medium (vendor page opened; study details from search summaries; the 2006 data predates agent-generated code and was observational)
- At Microsoft, defect finding is still the main stated reason for review, but reviews also give knowledge transfer, team awareness and alternative solutions, and understanding the code and the change is central; developers use many comprehension mechanisms that tools do not meet. — sources: https://2013.icse-conferences.org/content/expectations-outcomes-and-challenges-modern-code-review.html (2026-11-17) — confidence: high (abstract of the paper, opened)
- At Google, the study combined 12 interviews, a 44-respondent survey and logs of 9 million reviewed changes. A reader's notes report smaller changes than at other organisations, often one reviewer, fast first comments, and motivations ranked beyond bug finding (consistency, shared knowledge, test quality, accident prevention, gatekeeping). — sources: https://research.google/pubs/modern-code-review-a-case-study-at-google/ (2026-11-17), https://alastairreid.github.io/RelatedWork/papers/sadowski:icse-seip:2018 (2026-11-17) — confidence: medium (method from the official abstract; the findings from a secondary summary of the paper)
- Controlled experiment (50 participants, mostly professionals): review effectiveness is significantly larger for small changes; working memory capacity is moderately associated with finding delocalized defects (those visible only by inspecting non-contiguous parts); the effect of the order of change parts was inconclusive. — sources: https://www.zora.uzh.ch/entities/publication/245eb643-3ebd-476c-a613-8097ff6d9582 (2026-11-17), https://tobiasbaum.github.io/rp/memoryCodeOrderAndReview.pdf (2026-11-17) — confidence: medium (summary of the journal abstract from a search result; the paper was not opened)
- File position biases review: on 219,476 pull requests from 138 Java projects, files shown earlier received more comments; in an experiment with 106 participants, the odds of spotting one of two seeded defect types were 64% lower when its file came last than first (no effect for the other type). Tools list files alphabetically. A follow-up on one proprietary project found a weak correlation and proposed ordering by code-diff; a 2025 paper mines "meaningful" review orders from GitHub. — sources: https://arxiv.org/abs/2208.04259 (2026-11-17) — confidence: high (abstract of the 2022 paper opened; the follow-ups are known only from search-result titles and snippets, so treat them as low)
- Test-driven code review (read the changed tests before the production code): in a controlled experiment, reviewers found the same share of production defects and more defects in test code, with fewer maintainability issues found in production code; developers preferred production-first and cited poor test quality and no tool support. — sources: https://serg.ewi.tudelft.nl/publications/test-driven-code-review-an-empirical-study/ (2026-11-17), https://bibtex.github.io/ICSE-2019-SpadiniPBHBB.html (2026-11-17) — confidence: medium (search-result summaries of abstract; sample size differs between sources)
- Explicit review guidance (checklist, guided checklist) did not show a strong effect on performance in an experiment with mostly novice reviewers; its benefit depended on task complexity, and understanding the code mattered more than the guidance. — sources: https://link.springer.com/10.1007/s10664-022-10123-8 (2026-11-17), https://soroushjavdan.github.io/Do-Explicit-Review-Strategies-Improve-Code-Review-Performance (2026-11-17) — confidence: medium (summary of the abstract; the "understanding mattered more" point is from a blog review)
- Partitioning: ClusterChanges (Microsoft, ICSE 2015) decomposes a changeset by linking changed definitions and their changed uses, so unrelated parts can be reviewed independently. The abstract states reviews are harder when a changeset bundles unrelated changes; the evaluation used 1,000 Office changesets and a user study, and a replication on open-source Java found similar changesets. Related work finds that up to 15% of bug-fix commits in five Java projects mix several concerns, and that untangling had a 63–75% success rate in an earlier approach. — sources: https://www.microsoft.com/en-us/research/publication/helping-developers-help-themselves-automatic-decomposition-of-code-review-changesets/ (2026-11-17), https://www.st.cs.uni-saarland.de/publications/files/herzig-msr-2013.pdf (2026-11-17) — confidence: medium (abstract opened for ClusterChanges; evaluation numbers and the tangled-change figures from search summaries; all studies pre-date agent-generated changes)
- Risk-based ordering: in the effort-aware just-in-time defect prediction work, inspecting changes ranked by predicted risk covering 20% of the total effort found about 35% of defect-inducing changes; later work questions how applicable the effort-aware evaluation is in practice. — sources: https://xin-xia.github.io/publication/emse182.pdf (2026-11-17), https://quarxiv.authorea.com/doi/full/10.36227/techrxiv.171440925.50536437/v1 (2026-11-17) — confidence: medium (search-result excerpts; models were trained on human-written changes and use lines of code as the effort proxy)
- Review by exception exists as a team practice: Ship / Show / Ask lets the author choose per change between merging without review, merging with a review in parallel, or asking for review first. — sources: https://www.martinfowler.com/articles/ship-show-ask.html (2026-11-17) — confidence: medium (page and description from the search result; author-chosen category, no effectiveness data)
- Mutation testing in review: at Google, mutants are generated only for changed, covered, non-"arid" lines and surfaced during mandatory code review to about 6,000 engineers (more than 70,000 diffs, 1.1 million mutants, 150,000 actionable findings in the original evaluation). The authors study how it affects reviewer attention. — sources: https://research.google/pubs/state-of-mutation-testing-at-google/ (2026-11-17) — confidence: high (abstract opened for design and scale; the evaluation counts of 70,000 diffs, 1.1 million mutants and 150,000 findings come from a search summary of the paper)
- Volume pressure: Faros telemetry over more than 10,000 developers in 1,255 teams (data to June 2025) shows, for high-adoption versus low-adoption AI teams, 98% more merged pull requests, 91% longer review time, 154% larger average pull request and 9% more bugs per developer, and no significant link between AI adoption and company-level throughput or quality KPIs. Correlational, vendor telemetry. A later vendor report (two years, 22,000 developers) reports pull-request size +51% and median review time five times longer; not opened. — sources: https://www.faros.ai/blog/ai-productivity-paradox-report-2025 (2026-11-17), https://www.faros.ai/research/ai-acceleration-whiplash (2026-11-17) — confidence: medium (the 2025 report page was opened and states its method; the later report is known from a search snippet only and is low)
- Survey and practitioner writing (2026) converges on the claim that review, not generation, is the bottleneck, that reviewing AI code is more effortful and loses intent ("reviewer is left reverse-engineering intent from a diff"), and that uniform review is the wrong answer: risk tiers (a four-tier scheme from line-by-line for auth, payments, migrations and public APIs down to auto-approval of boilerplate when CI passes), automated first-pass gates, spec-first intent check, author must explain the approach, source-agnostic review. Statistics in these posts are mostly vendor survey numbers (for example 38% of developers say reviewing AI code takes more effort than a colleague's; 96% do not fully trust it) and some are traced to no primary study. — sources: https://codex.danielvaughan.com/2026/05/24/human-review-bottleneck-code-review-strategies-agent-output/ (2026-11-17), https://www.sonarsource.com/ko/blog/how-to-scale-code-quality/ (2026-11-17), https://thenewstack.io/ai-code-review-burnout/ (2026-11-17) — confidence: low (blogs and vendor posts; the New Stack page returned HTTP 403, so its quotes come from a search snippet)
- Controlled and field studies of LLM help in review give mixed signals: in an experiment with 29 developers, reviewers kept 89% of the LLM's issues but found no more high-severity issues than fully manual reviewers; in a field study at one company (ten participants), developers wanted clearer up-front summaries of changes and on-demand explanations, and preferred AI-led reviews depending on codebase familiarity and severity. No study found measures the effect of an LLM change summary on comprehension. — sources: https://arxiv.org/pdf/2505.16339 (2026-11-17), https://arxiv.org/abs/2505.16339 (2026-11-17) — confidence: medium (abstract opened for the field study; the 29-developer figures are from a search snippet of a different paper)
- Provenance: Entire's checkpoints link each commit, by an `Entire-Checkpoint` trailer, to the agent session behind it: prompts, transcript, tool activity, changed files, token usage and line-level AI attribution; a reviewer can read the transcript, trace code to context and run `entire blame`. Metadata lives on a separate ref or branch, not on the working branch. — sources: https://docs.entire.com/guides/checkpoints/overview (2026-11-17) — confidence: high (official documentation, opened; product is new)
- Agent Trace is an open specification (v0.1.0 RFC proposed by Cursor, with Cognition among supporters) for records that link code ranges to the conversations and contributors (human, AI, mixed, unknown) behind them. It prescribes no storage. Thoughtworks put it in "Assess" in April 2026, noting early adoption. — sources: https://www.thoughtworks.com/radar/platforms/agent-trace (2026-11-17), https://github.com/cursor/agent-trace (2026-11-17) — confidence: medium (Radar page opened; spec details from search snippets)
- No study found tests whether giving reviewers the agent transcript improves defect finding or review speed; the sources describe capture and attribution, not outcomes. — sources: https://docs.entire.com/guides/checkpoints/overview (2026-11-17), https://www.thoughtworks.com/radar/platforms/agent-trace (2026-11-17) — confidence: low (inference from absence in the sources opened)
- Runtime evidence made by the agent: a practitioner guide has the agent run its code manually (curl against a dev server, scripts, browser automation with screenshots) and record the commands with their real outputs in a markdown document, so a reviewer sees what was run and what happened; bugs found become permanent automated tests. The tool executes the command itself so the agent cannot write the expected output instead. — sources: https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing (2026-11-17) — confidence: medium (primary description of a practice by one practitioner; no effectiveness data)

## Confidence
Overall: medium for the SDD tool landscape (official pages for Kiro and Spec Kit's README; the other three tools through AI-generated repository summaries), medium for the established empirical review findings (most from abstracts and summaries, not full papers), low for 2026 claims about AI-code review at scale (vendor and blog sources). The pre-2020 studies concern human-written changes of a few hundred lines; whether their effects extend to agent-written changes of thousands of lines is an inference.

What would raise it: reading the full Google, Baum, Spadini and Gonçalves papers; running Spec Kit converge, OpenSpec verify and Kiro's property tests on a sample change to see their real output; the Faros and Qodo primary reports; any study measuring the effect of transcripts or LLM summaries on review outcomes.

## Implications
- Size evidence points one way. Effectiveness and inspection rate fall as the change grows (200–400 lines, under about 500 lines an hour; small changes more effective; working memory limits delocalized defects). A multi-thousand-line agent change cannot be reviewed line by line at these rates, so partitioning, ordering and evidence-based acceptance are research-backed levers, not just ideas. This supports the problem statement's scale driver.
- Review is more than bug finding (comprehension, knowledge transfer, consistency). A paradigm that replaces reading with evidence must say who still learns the code; this is a risk for any "accept on evidence" workflow.
- SDD tools verify code against the spec inside the agent's loop; none opened gives the developer a coverage view over a large diff (low confidence, see Findings). The "specs when present, intent fallback otherwise" decision means the design needs one neutral intermediate form (requirement or intent items with evidence) that both an SDD workspace and an intent extracted from commits and transcripts can fill. This note does not decide that form.
- Spec review is itself costly (Böckeler's experience; verbose spec files). A tool that leans on specs should help review the spec delta as well, not assume the spec is correct.
- Provenance capture exists (Entire, Agent Trace) and could feed an intent fallback; its benefit to review is not measured. Reading transcripts could also add load; this needs a test.
- Evidence signals exist at several levels (tests linked to requirements, property counter-examples, surviving mutants on changed lines, agent-recorded manual runs, formal proofs for small critical kernels). They differ in cost and in how far the reviewer must trust the agent that produced them.
- LLM-generated review content may narrow attention without finding more serious defects (one experiment). A workflow that relies on LLM explanation needs a way to show uncertainty and to let the reviewer sample the underlying code.
- Related IDs: feeds the problem statement and options analyses of CHG-001 (the two option analyses named in the brief); no ID is created or changed here.

### Candidate paradigms (brainstorm; no ranking, no form factor)
Each line: idea — source or analogue — what it changes for a developer accepting a huge agent change.

1. Intent-first review: start from a list of intended outcomes (spec items, or intent extracted from prompt, commit text or transcript) and open code only to answer "is this outcome met?" — BMAD intent-alignment lens, spec-first step in practitioner guides — the developer reads dozens of claims, not thousands of lines.
2. Requirement coverage map: a matrix of requirement to code regions to tests or evidence, with unmet and unverified items on top — traceability definition, Kiro property links, OpenSpec "Not verified" — the developer sees what is proven, claimed, or missing.
3. Orphan-code detector: flag code that traces to no requirement or intent item (scope creep, unrequested refactors, unspecified behaviour) — orphaned-ID checks in practitioner guides, Spec Kit analyze — the developer's attention goes first to what nobody asked for.
4. Semantic partitioning into independent review units: group hunks by definition and use links, by task, or by requirement — ClusterChanges, untangling research — one huge diff becomes a queue of small reviewable units, each verdict independent.
5. Risk-tiered review with review-by-exception: score each unit (sensitive area, size, novelty, test coverage, dependency changes), review the top tier fully, skim the middle, auto-accept the bottom when checks pass — just-in-time defect prediction, tier scheme in 2026 practitioner writing, Ship/Show/Ask — human time is spent where predicted risk is, with an explicit residual-risk statement.
6. Test-first reading order: read acceptance scenarios and tests before implementation, and review whether the tests express the intent — test-driven code review, Gherkin as executable spec — the developer judges the contract, then the machine checks the code against it.
7. Executable evidence bundle: the agent must deliver re-runnable proof (recorded commands and real outputs, screenshots, API traces) attached to each unit — agentic manual testing with recorded exec — acceptance means re-running evidence and inspecting a sample, not trusting a summary.
8. Test-adequacy evidence on the changed lines: show surviving mutants or failing property counter-examples next to the unit — mutation results in review at Google, Kiro property tests with shrinking — the developer learns whether the tests would notice a wrong change before trusting "all tests pass".
9. Independent verifier with adversarial lenses: a second agent with a different brief (adversarial, edge cases, verification gaps, intent) attacks each unit, and the developer adjudicates disputed findings — BMAD lenses, implementer/verifier separation — review becomes arbitration of a short list of contested points; limited by LLM review quality evidence.
10. Provenance-linked hunks: each hunk links to the prompt and transcript segment that produced it, with markers where the agent retried, guessed or contradicted itself — Entire checkpoints, Agent Trace — the developer can ask "why was this written?" without reverse-engineering intent; benefit unproven.
11. Narrative walkthrough in dependency order: an ordered story of the change (what, why, in what order), each step opening its code — BMAD walkthrough, LLM summaries wanted in the field study — addresses file-order bias and comprehension, at the risk of the narrative hiding problems.
12. Behavioural diff instead of source diff: compare observed behaviour before and after (API responses, outputs, public-interface surface, golden outputs) — approval or golden-master testing (an analogue, not researched in this note) — the developer reviews what the system now does, which the agent's size does not inflate.
13. Spec-delta review: review the spec change (added, modified, removed requirements) and the conformance evidence, treating code as a checked artifact — OpenSpec delta specs, Tessl spec-as-source aspiration — shrinks the review surface to the spec delta; relies on the spec being trusted and on conformance checks being real (Böckeler found agents do not always follow specs).
14. Review during generation: checkpoints at each agent task, with the developer accepting small increments while the agent continues — Kiro task-by-task execution, Entire per-commit checkpoints, plan and spec review before generation — the size problem is cut at the source because no unit ever becomes huge.
15. Sampling with escalation: review a random 20–33% of low-risk units; one confirmed defect escalates the class to full review — spot checking in the SmartBear material; acceptance sampling in quality control (an analogue, not researched) — gives a stated confidence level for the rest instead of an unexamined bulk.
16. Attention-budget planner: the tool knows the developer's time and a sustainable inspection rate, orders units by value per minute and shows covered versus uncovered risk — inspection-rate guidance, effort-aware ranking — turns "I skimmed it" into an explicit, bounded coverage statement.
17. Order-by-importance, not alphabet: present core logic and risky units first, mechanical changes last — file-position bias study and its follow-ups — avoids the measured loss of defect detection for later files.
18. Formal contract for critical kernels: express selected requirements as contracts or proofs the machine checks — vericoding benchmark, Dafny and Verus — for small high-stakes units the developer reviews the spec, not the implementation; narrow reach today.
19. Interrogation mode: the developer questions the change (agent plus transcript plus code index) and the answers cite code and evidence — on-demand explanation prototype in the field study — comprehension on demand replaces reading everything; trust and false-positive concerns noted by the study.
20. Verdict ledger with incremental re-review: store the verdict and evidence per unit, and when the agent revises, re-present only units whose content, evidence or traced requirement changed — Spec Kit and OpenSpec iterate-until-converged loops, review-state tracking — the developer never re-reads accepted work after the agent's fix cycle.

## Conflicting evidence
- Spec Kit commands: the repository README lists converge and no analyze or checklist command, while the knowledge base documents all three. Weighed in favour of the README for what is currently listed, and in favour of the knowledge base for the existence of analyze and checklist as earlier commands; unresolved. The tool's current command set should be checked in a real run.
- Kiro dates: a search summary gives general availability on 2025-11-17 and another source an international launch on 2026-05-07. Unresolved, and not needed for this note.
- Faros figures: the main text gives +91% review time, one table elsewhere +441%, and the 2026 follow-up a fivefold rise; different periods and metrics. The opened 2025 page was used and the others not relied on.
- Checklists and guidance: practitioner posts advise checklists and tiers, while the one controlled study found no strong effect of guidance on performance (mostly novices). Weighed as "unproven", not "ineffective".
- Specs versus code as the review target: the independent Kiro/Spec Kit/Tessl assessment prefers reviewing code over verbose markdown, while vendors and practitioners advise reviewing the spec first. Left open; the choice depends on spec quality.
- Review time versus size claims: SmartBear's page does not attribute every figure to the Cisco study, and secondary posts add figures (detection-rate tables by size) not supported by the summaries. Those added figures were excluded.
