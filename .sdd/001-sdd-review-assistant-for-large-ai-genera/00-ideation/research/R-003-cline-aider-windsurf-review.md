# R-003 — How Cline, Aider and Windsurf present agent changes for review and acceptance

## Question
Brief (verbatim): "How do Cline, Aider and Windsurf present agent changes for review and acceptance?" For each tool: the review unit (edit, hunk, file, turn, task); when review happens (before apply, after apply, at checkpoints, at commit); accept/reject granularity and controls; checkpoints, undo and rollback; git integration; plan versus act modes or approval settings; behaviour on large multi-file changes; spec or intent awareness; deployment and licence (flag copyleft, which the constitution forbids as a dependency). End with a comparison table in the columns of C001-R-001 §E and a short list of ideas or gaps relevant to CHG-001, cross-referencing C001-R-001's gap numbers.

Why asked: ad-hoc extension of C001-R-001 §C after gate G1 of CHG-001. It extends the survey of agent-tool review surfaces with three tools that R-001 did not cover. It serves the design direction of the ideation (§8: intake, intent map, risk triage, verdict) and the licence rule of the constitution (forbidden technologies: copyleft dependencies). No form factor is recommended here.

## Method
- Routing: Cline (`cline/cline`) and Aider (`Aider-AI/aider`) are public repositories, so the first source was the repository knowledge base (DeepWiki, one `ask_wiki_question` call each, 2026-11-17). Windsurf is a product, so the first source was web search. Context7 was not used (no library API is asked about).
- DeepWiki answered the behaviour questions but could not state either licence ("the provided context does not identify the licence"). The licences, and every behaviour that matters to a decision, were then confirmed on the primary pages: the repositories on GitHub, Cline's documentation (docs.cline.bot), Aider's documentation (aider.chat) and Devin Desktop's documentation (docs.devin.ai), all fetched on 2026-11-17.
- Naming fact found during the work: Windsurf was renamed Devin Desktop on 2026-06-02 and the Cascade agent was replaced by Devin Local (see Findings, Windsurf). Findings use "Windsurf (Devin Desktop)" and name the agent explicitly.
- Caveat on method: the fetch tool returns a summary produced by a small model, not the raw page. Facts that matter to a decision (defaults, licences) should be re-read on the vendor page before they are relied on. A web search answer was used only to locate pages; every cited behaviour below comes from a page opened afterwards, except where marked "search result only".
- Not reached: Cline's SDK permission-handling guide, Cline VS Code per-hunk behaviour in the diff editor (docs silent), Windsurf/Devin Desktop licence terms and data-processing terms, Devin Local plan-mode page, any size limit or measured behaviour on 100+ file changes for any of the three tools.
- Access date for every source: 2026-11-17. No instructions were found in the web content read.

## Findings

### A. Cline (VS Code and JetBrains extension, CLI, Kanban)

- Review unit and timing, extension: the unit is one tool action (one file creation or edit, one terminal command). The proposed change is shown as a diff in the editor or chat with Approve and Reject; nothing is written until the user approves, unless auto-approve covers it. Review is therefore before apply, per edit. — sources: https://docs.cline.bot/usage/ide (2026-11-17), https://github.com/cline/cline (2026-11-17), DeepWiki answer for cline/cline https://deepwiki.com/search/f59ba9a5-2142-4925-a7ff-836e55b49bad (2026-11-17) — confidence: high (official documentation and README agree)
- Granularity: Approve and Reject act on a whole proposed edit (a file-level change). The IDE page does not describe per-hunk accept inside an edit or editing a proposal before approval; DeepWiki says the diff can be reviewed, edited or reverted, which the IDE page does not confirm. — sources: https://docs.cline.bot/usage/ide (2026-11-17), https://deepwiki.com/search/f59ba9a5-2142-4925-a7ff-836e55b49bad (2026-11-17) — confidence: medium (absence in docs is not proof; DeepWiki claim unconfirmed)
- Approval settings: by default every file edit and terminal command needs approval. Auto Approve categories: "Read project files", "Read all files", "Edit project files", "Edit all files", "Execute safe commands", "Execute all commands", "Use the browser", "Use MCP servers", "Enable notifications"; the "all files" options apply only to paths outside the workspace and depend on the base toggle. "YOLO Mode" auto-approves everything, including file changes, commands, MCP and mode transitions. With auto-approve on, changes reach the working tree with no review step; review then happens only through checkpoints or git. — sources: https://docs.cline.bot/features/auto-approve (2026-11-17), https://github.com/cline/cline (2026-11-17) — confidence: high (official documentation)
- Plan versus Act: in Plan mode Cline reads and searches but "cannot modify any files or execute commands"; in Act mode it edits, still subject to approval. History carries over; a different model can be set per mode. The docs describe no dedicated plan view; they suggest writing the plan to a markdown file and keeping a todo list. `/deep-planning` runs an extended planning session that identifies affected files and dependencies and creates an implementation plan before work, recommended for tasks spanning many files. — sources: https://docs.cline.bot/core-workflows/plan-and-act (2026-11-17) — confidence: high (official documentation)
- Checkpoints and rollback: enabled by default. After each tool use (file edits, commands and others) Cline commits the full file state to a shadow Git repository kept separate from the project's own history; checkpoints persist across editor sessions. "Compare" opens the editor's diff viewer across all affected files; "Restore Files" reverts files and keeps the conversation, "Restore Task Only" rewinds messages and leaves files, "Restore Files & Task" does both. The page says that for very large repositories checkpoints "may use significant storage and slow down Cline" and suggests disabling them; it states no count, retention or size limit. Because the snapshot is taken after commands as well as edits, this tracking is wider than the checkpoint holes R-001 §D records for Claude Code and the VS Code working set; whether it captures every shell-made change was not tested. — sources: https://docs.cline.bot/features/checkpoints (2026-11-17), https://docs.cline.bot/usage/ide (2026-11-17) — confidence: medium (the documented behaviour is stated by the vendor page, but the comparison with other tools is an untested inference)
- Git integration: the extension does not commit to the project's history; checkpoints are a separate shadow repository and "do not replace" normal commits (DeepWiki note). The user's own git, or in Kanban the agent, performs commits. — sources: https://docs.cline.bot/features/checkpoints (2026-11-17), https://deepwiki.com/search/f59ba9a5-2142-4925-a7ff-836e55b49bad (2026-11-17) — confidence: high (documentation and DeepWiki agree)
- Large multi-file changes, extension: no special behaviour found. Each file edit is approved one at a time (or auto-approved); Compare gives a combined diff over a checkpoint. DeepWiki found no documented large-change handling. — sources: https://deepwiki.com/search/f59ba9a5-2142-4925-a7ff-836e55b49bad (2026-11-17), https://docs.cline.bot/features/checkpoints (2026-11-17) — confidence: medium (absence of evidence)
- Cline Kanban (research preview, local web app started with `npx kanban`): each card is a task; starting it creates an ephemeral git worktree, so parallel agents do not conflict. Opening a card shows the agent's terminal and a diff against the base branch; checkpoints let the user scope the diff to a range of messages; the user can comment on any diff line and "Comments are sent back to the agent as feedback". Acceptance is either committing the worktree changes to the base branch or opening a PR from a new branch, performed by the agent. Cards can be linked into dependency chains; the next task starts when a linked card is moved to trash. Works with Cline CLI, Claude Code, Codex, OpenCode. Review unit: task (a worktree diff), with line comments. — sources: https://docs.cline.bot/kanban/core-workflow (2026-11-17), https://docs.cline.bot/kanban/overview (2026-11-17), https://github.com/cline/kanban (2026-11-17) — confidence: high (three pages agree; the project is a research preview and "may change")
- Spec or intent awareness: none found for review. The nearest items are the plan markdown file and `/deep-planning` output (an intent source before code, not linked to hunks) and Kanban cards (a task is the unit of work and of review, but no requirement link is described). — sources: https://docs.cline.bot/core-workflows/plan-and-act (2026-11-17), https://docs.cline.bot/kanban/core-workflow (2026-11-17) — confidence: medium (absence across pages read)
- Deployment and licence: VS Code extension, JetBrains, CLI (`npm i -g cline`, interactive or headless for CI) and Kanban (local server, Node.js 18 or later, git repository). Both `cline/cline` and `cline/kanban` are Apache-2.0 (copyright Cline Bot Inc.). Permissive; no copyleft flag. Model providers are configured by the user. — sources: https://github.com/cline/cline (2026-11-17), https://github.com/cline/kanban (2026-11-17), https://docs.cline.bot/kanban/overview (2026-11-17) — confidence: high (licence shown on both repository pages; licence text itself not opened)

### B. Aider (terminal pair-programming tool)

- Review unit and timing: the unit is the edit set of one agent turn, committed to git. Aider applies the model's edits to files and, by default, commits them at once with a descriptive message (Conventional Commits by default). Review is after apply, through `/diff` or normal git tools. The documentation does not describe a pre-apply approval step: the chat-modes page mentions none, and DeepWiki found none. — sources: https://aider.chat/docs/git.html (2026-11-17), https://aider.chat/docs/usage/modes.html (2026-11-17), https://deepwiki.com/search/db4da100-337c-407a-b911-b39a479f17cb (2026-11-17) — confidence: medium (primary pages state the commit behaviour; "no approval step" rests on absence)
- Accept/reject controls: none beyond undo. `/diff` shows "all the file changes since the last message you sent"; `/undo` undoes the last git commit "if it was done by aider" (one commit at a time, never the user's commits); `/git` runs raw git; `/commit` commits changes made outside the chat. Acceptance is implicit (the commit stays); rejection is `/undo` or `git revert`/`reset`. Granularity is the commit, not the hunk. — sources: https://aider.chat/docs/usage/commands.html (2026-11-17), https://aider.chat/docs/git.html (2026-11-17) — confidence: high (official documentation)
- Checkpoints and git: git is the checkpoint mechanism. Before editing a file that has uncommitted changes, Aider first commits those changes separately ("`--no-dirty-commits`" turns this off), keeping the user's work and the agent's edits apart. Aider's commits carry "(aider)" on the author and committer names (options for a co-author trailer or message prefix exist), so agent work is separable in history. `--no-auto-commits` stops per-edit commits; `--dry-run` is documented as a run without modifying files, and commits are skipped in dry run. — sources: https://aider.chat/docs/git.html (2026-11-17), https://deepwiki.com/search/db4da100-337c-407a-b911-b39a479f17cb (2026-11-17) — confidence: high (the commit behaviour is on the official page; the `--dry-run` detail is only partly shown by DeepWiki)
- Modes and approval: `code` edits; `ask` never edits; `architect` uses an architect model to propose a solution and an editor model to turn it into file edits (two requests); `help`. The architect proposal is a plan in text, but no confirmation step is documented. Edit formats (`whole`, `diff`, `diff-fenced`, `udiff`, `editor-diff`, `editor-whole`) define how the model expresses edits; an edit that does not match the file is not written and Aider reports "Failed to apply edit". — sources: https://aider.chat/docs/usage/modes.html (2026-11-17), https://aider.chat/docs/more/edit-formats.html (2026-11-17), https://aider.chat/docs/troubleshooting/edit-errors.html (2026-11-17) — confidence: high (official documentation)
- Automated checks: linting of edited files is on by default (`--no-auto-lint` disables it); tests run with `/test` or after every edit with `--test-cmd` and `--auto-test`; on a non-zero exit Aider tries to fix the errors. The docs do not say whether commits happen when lint or tests fail; `/diff` includes changes from lint and test fixes (DeepWiki). — sources: https://aider.chat/docs/usage/lint-test.html (2026-11-17), https://deepwiki.com/search/db4da100-337c-407a-b911-b39a479f17cb (2026-11-17) — confidence: medium (documentation silent on failure path)
- Large multi-file changes: Aider builds a repository map for context (`/map`) and offers `--subtree-only` for large repositories. DeepWiki found no special apply or review strategy for large multi-file edits. With per-turn commits a large change becomes a series of commits that can be read or reverted individually. — sources: https://deepwiki.com/search/db4da100-337c-407a-b911-b39a479f17cb (2026-11-17), https://aider.chat/docs/git.html (2026-11-17) — confidence: medium (absence of evidence; series-of-commits is an inference from the documented behaviour)
- Spec or intent awareness: none found. The nearest item is the architect proposal text; commit messages are written by a model from the diff and chat history. — sources: https://aider.chat/docs/git.html (2026-11-17), https://aider.chat/docs/usage/modes.html (2026-11-17) — confidence: medium (absence across pages read)
- Deployment and licence: local command-line tool (`pip install aider-install`, package `aider-chat`), any cloud or local model, runs inside the developer's git repository. The GitHub page labels the repository "Apache-2.0 license". Permissive; no copyleft flag. — sources: https://github.com/Aider-AI/aider (2026-11-17) — confidence: high (licence label on the repository page; licence text itself not opened)

### C. Windsurf (now Devin Desktop; Cascade replaced by Devin Local)

- Naming and status: Windsurf was renamed Devin Desktop on 2026-06-02, built on Windsurf's IDE foundation, with an Agent Command Center (all local and cloud agents on one board) and support for third-party agents through the Agent Client Protocol. Devin Local, a Rust rewrite with subagents, replaced Cascade as the primary local agent. The blog said Cascade stays available through July 1; the changelog states Devin Local became the only agent on 2026-09-08 and "Cascade has been removed". Existing Windsurf plans and features were stated to continue. Questions about "Windsurf Cascade" therefore concern a legacy agent; the current surface is Devin Local. — sources: https://devin.ai/blog/windsurf-is-now-devin-desktop (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17), https://docs.devin.ai/desktop/cascade/cascade (2026-11-17) — confidence: high (vendor blog, changelog and documentation agree)
- Review unit and accept/reject, current: agent edits can show as "agent diff zones", inline highlighted regions in the editor with accept and reject controls "for each hunk". The documentation page ("advanced") says all agents use diff zones by default, but the changelog says that since 2026-10-23 (v3.11.212) "Agent diff zones are off by default, so agent edits are applied directly to files"; with zones off the toolbar shows a simple dismiss button instead of accept/reject, and diff zones close automatically on commit (2026-02-12). The user can re-enable them in Devin Settings under Editor > User Interface. Review is after apply in the default configuration; before-apply, per-hunk review only if the setting is turned back on. — sources: https://docs.devin.ai/desktop/advanced (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17) — confidence: medium (the changelog is dated and newer than the advanced page; the reason for the change is not stated)
- Checkpoints and rollback (legacy Cascade page): hover over a prompt and click the revert arrow, or revert from the table of contents; named checkpoints can be created; "Reverts are currently irreversible." Since 2026-08-10 (v3.7.16) revert buttons appear as soon as a prompt is sent. Cascade could work in an isolated git worktree and "merge" back. The Devin Local equivalent of checkpoints was not documented in the pages read. — sources: https://docs.devin.ai/desktop/cascade/cascade (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17) — confidence: medium (legacy page; applicability to Devin Local not confirmed)
- Approval settings and plan mode: terminal commands follow Allow, Deny and Ask rules (`Exec(git status)` syntax) configured in Devin Local settings; for commands no rule covers, session modes are Code (asks), Smart (a fast model auto-approves commands it judges safe) and Bypass Permissions (runs unless organisation policy requires approval). Organisation deny and ask rules override a member's rules and Bypass Permissions. Keyboard shortcuts for accepting and rejecting permission requests exist since 2026-07-29. Plan mode was improved on 2026-08-21 (v3.8.19) with a full Markdown plan file and an explicit Implement button. Cascade kept a "Todo list" refined by a background planning agent. — sources: https://docs.devin.ai/desktop/terminal (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17), https://docs.devin.ai/desktop/cascade/cascade (2026-11-17) — confidence: high (vendor documentation and changelog)
- Review of a whole change: two separate tools. Quick Review runs an agentic review of the local diff made by Devin Local: after the agent's edits the user selects Quick review and a review model (SWE-check, free on paid plans and trials; GPT-5.5 Review and Opus 4.7 Review, billed by token), and feedback appears inline in the editor before commit; it is enabled by default for enterprise organisations and is not available for the legacy Cascade agent. Devin Review (pull requests; described in C001-R-001 §A) groups related edits by the logic of the change and shows moves as moves; it was available to all self-serve users from 2026-05-06; the Windsurf blog describes it for pull requests and states no size limits. — sources: https://docs.devin.ai/desktop/quick-review (2026-11-17), https://devin.ai/blog/devin-review-windsurf (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17) — confidence: high (vendor pages agree)
- Large multi-file changes: no per-size behaviour is documented for the local agent. The vendor's answer for large diffs is Devin Review, which groups edits on a pull request; Quick Review gives findings, not a grouped structure, in the pages read. — sources: https://devin.ai/blog/devin-review-windsurf (2026-11-17), https://docs.devin.ai/desktop/quick-review (2026-11-17) — confidence: medium (absence of documented size handling)
- Spec or intent awareness: rules files are read as context: `AGENTS.md`, `AGENTS.local.md`, `AGENT.md` (always on, at the workspace root and in directories down to the working directory), legacy `.windsurf/rules/` and `.devin/rules/` with activation modes always_on, glob, model_decision and manual. Workflows are markdown files invoked by `/name` (12,000 characters each in the legacy page). No link from hunks to requirements or specifications is described. — sources: https://docs.devin.ai/desktop/cascade/memories (2026-11-17), https://docs.devin.ai/desktop/cascade/cascade (2026-11-17) — confidence: medium (absence across pages read; the page itself says it does not mention spec or plan awareness)
- Deployment and licence: a desktop IDE (a Windsurf/VS Code-based editor) with cloud agents, models and review services billed by plan or token. The pages read state no licence for Devin Desktop; it is treated as proprietary, so it cannot be a dependency and is inspiration only. — sources: https://devin.ai/blog/windsurf-is-now-devin-desktop (2026-11-17), https://docs.devin.ai/desktop/quick-review (2026-11-17) — confidence: low (licence absent from the pages read; proprietary status inferred)

### D. Cross-cutting observations

- The three tools put review at three different moments: Cline before apply (per action, with a checkpoint trail), Aider after apply with git as the record (per turn, per commit), Devin Desktop after apply by default since 2026-10-23 (diff zones off), with an optional secondary review agent. None groups changes by intent or requirement inside the agent surface; grouped review (Devin Review) is a separate pull-request product. — sources: https://docs.cline.bot/usage/ide (2026-11-17), https://aider.chat/docs/git.html (2026-11-17), https://docs.devin.ai/desktop/changelog (2026-11-17), https://devin.ai/blog/devin-review-windsurf (2026-11-17) — confidence: medium (synthesis across vendor pages)
- Two of the three support full autonomy by configuration (Cline YOLO Mode and "Execute all commands"; Devin Local Bypass Permissions; Aider commits without asking). In these settings the developer's first look at a large change is after it has landed, which is the intake situation of the ideation (§8 step 1). — sources: https://docs.cline.bot/features/auto-approve (2026-11-17), https://docs.devin.ai/desktop/terminal (2026-11-17), https://aider.chat/docs/git.html (2026-11-17) — confidence: medium (synthesis; inference about usage patterns)
- Three tools expose a task or turn boundary that could be a grouping signal for later analysis: Cline checkpoints (a diff scoped to a range of messages), Cline Kanban cards (one worktree per task), Aider commits (one per turn). — sources: https://docs.cline.bot/kanban/core-workflow (2026-11-17), https://docs.cline.bot/features/checkpoints (2026-11-17), https://aider.chat/docs/git.html (2026-11-17) — confidence: medium (documented boundaries; their value as a grouping signal is an inference)

## Confidence
Overall: medium. Behaviour descriptions come from vendor documentation and changelogs fetched on 2026-11-17 and are strong for what each tool documents (high for approvals, checkpoints, git commands, licences of Cline, Kanban and Aider). They are weak on large-change behaviour, because no page states any size handling for the three tools, and on Devin Desktop's licence. The Windsurf surface changed during 2026 (rename, Cascade removed, diff zones off by default), so older third-party guides are unreliable for it. What would raise confidence: a hands-on trial of each tool on a 50+ file change, reading the licence files of the three repositories, and confirming Devin Local's checkpoint and diff behaviour in the current application.

## Implications
- Ideation fit: none of the three tools covers intake of a large change after the fact, grouping, intent mapping or verdict recording; this confirms the space left open in C001-R-001 §Implications and does not change the design direction of the ideation §8.
- Licence: Cline, Cline Kanban and Aider are Apache-2.0 (permissive) and could be references or dependencies without breaching the constitution (NFR-D-03); Devin Desktop is proprietary and is inspiration only. No copyleft component was found in these three. The licence files themselves were not opened.
- Gaps and ideas, with C001-R-001 gap numbers:
  1. Gap 1 (local, pre-commit restructured review) is only partly met by Quick Review, which is local but returns findings inline, not an ordered grouped structure.
  2. Gap 2 (spec mapping) stands: no hunk-to-requirement link exists in any of the three. Plan files (Cline plan markdown and `/deep-planning`, Devin Local plan file, Aider architect proposal) are an agent-plan input for the intent fallback of ideation §8 step 1.
  3. Gap 3 (durable verdict ledger) stands: accept is implicit (an Aider commit, a Cline approval, a Devin dismiss); none records a verdict per intent.
  4. Gap 6 (agent's account versus the diff): turn and task boundaries (Aider commits, Cline checkpoints, Kanban cards) give provenance, "which agent step produced this hunk", which could support comparing the agent's account with the diff. Whether this is useful for intent mapping is an open design question, not a finding.
  5. Gap 7 (structured feedback loop): Cline Kanban already sends line comments back to the agent; this is a stronger precedent than those listed in R-001 and bears on the "Later" item in ideation §5.
  6. Gap 8 (changes invisible to checkpoints): Cline's checkpoints are taken after commands as well as edits, so R-001's statement that agent-tool checkpoints have holes is tool-specific. A working-tree-versus-base comparison still avoids reliance on any agent tool's own tracking; the claim that Cline has no hole is untested.
  7. Aider's practice of committing the user's dirty files separately before agent edits is a cheap way to give an intake step a clean base commit; relevant to the intake design (ideation §8 step 1) and to the open question on where verdicts are stored (ideation §11).
  8. A vendor made per-hunk diff zones non-default (2026-10-23) with no stated reason. One possible reading, that per-hunk acceptance does not scale to agent output, is an inference; it would support the ideation's premise that hunk-by-hunk reading is not the unit to build on, but it is not evidence of that.
- Risk: approvals by action (Cline) and permission modes (Devin) control what the agent may do, not whether a person reviewed the result; a review assistant that assumes pre-apply approval has occurred will misjudge users who run auto-approve or Bypass Permissions.

## Conflicting evidence
- Devin Desktop diff zones default: the "advanced" documentation page says all agents use diff zones by default; the changelog says they have been off by default since 2026-10-23. The changelog is dated and newer, so it was preferred; the advanced page may be stale.
- Cascade availability: the rename blog says the legacy Cascade agent remains available through July 1; the changelog says Cascade was removed on 2026-09-08 and legacy entry points on 2026-09-10; the Cascade page itself says Devin Desktop no longer starts new Cascade conversations. Changelog and page preferred (they agree with each other).
- Cline edit proposals: DeepWiki says the diff can be reviewed, edited or reverted by the user; the IDE page describes only Approve and Reject and does not say whether a proposal can be edited. The documentation was preferred; editing before approval is unconfirmed.
- Windsurf accept/reject granularity: third-party guides disagree (per file versus per hunk) and on keyboard shortcuts; they were not relied on. The vendor documentation states per hunk for diff zones.
- Cline checkpoints page naming: the IDE page lists restore options as "Task and Workspace, Task Only, Workspace Only", the checkpoints page as "Restore Files, Restore Task Only, Restore Files & Task". The same three behaviours; the checkpoints page wording was used.

## Follow-up questions
- How do Cline, Aider and Devin Local behave on a real 50+ file, 10,000-line agent change (review time, diff usability, checkpoint cost)? A hands-on trial would answer it.
- What does Devin Local use for checkpoints and rollback, and does a "Review" tab show the whole change grouped?
- Does Cline's VS Code diff editor allow per-hunk reject or edit before approval?
- What are the licence terms and data-processing locations of Devin Desktop and of Quick Review (local diff sent to a cloud review model)?
- Do Aider's lint and test failure paths commit, and how does `/undo` behave after several consecutive commits? A hands-on check would answer it.
